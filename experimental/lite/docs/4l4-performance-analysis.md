# Four-L4 collective performance analysis — 2026-11-13

The strongest opportunity is large ReduceScatter and small-message submission/synchronization. Large AllReduce already approaches the measured bandwidth of its ring schedule. AllGather's host-packet path already avoids much of the direct-peer bottleneck. A single PCIe bandwidth number is not an upper bound for every algorithm: routes, direction, host participation, and simultaneous traffic matter.

This audit covers the current standalone FP32 `allreduce.cu` and `peer_ag_rs.cu`, plus the optional FP32 bit-copy packet AllGather. The BF16 CPU-router experiments are separate evidence, not interchangeable performance or numerical contracts. No collective implementation was changed. Existing untracked two-GPU experiments were left untouched.

**Evidence and timing.** Current revision and source/binary/library hashes are in [identity.json](../benchmarks/data/analysis_4l4_20261113/identity.json). The local host is `mibura-sky-test-02`: four L4s, dual Xeon Silver 4410Y, NUMA pairs (0,1)/(2,3), PCIe Gen4 x16, peer access across all pairs, driver 595.58.03, CUDA runtime 12.9. `make hardware_profiler peer_ag_rs allreduce` found the targets up to date. The fresh native AR run uses 2 warmups and 3 timed calls per variant (one window, no paired NCCL run), with full output checks and zero reported relative error. The new hardware run has 2 warmups, 10 iterations and 3 repetitions; the peer run has 2 warmups, 5 calls and 3 rotated repetitions per backend, with full checks on every call. Allocation, input fill and checks are excluded. Peer timing is maximum per-rank CUDA-event duration, including enqueue gaps; AllReduce uses maximum-rank host enqueue-to-completion time. They are not directly comparable latency measurements. No variant selection is needed in the new large peer sweep; the archived selected curves choose the fastest correct UCCL variant per size.

**Bounds and attainable targets.** Let N denote full input bytes for AR/RS and full output bytes for AG. Each AG input and RS output is N/4. GB/s is decimal; GiB is binary. Conventional bus bandwidth is 1.5N/t for AR and 0.75N/t for AG/RS. It is a normalization, not measured wire traffic.

For balanced GPU-only reduction/forwarding, minimum total nonlocal useful traffic is 6N for AR and 3N for AG/RS. With per-GPU outgoing capacity B and no other bottleneck:

```
t_AR >= 1.5 N / B
t_AG,RS >= 0.75 N / B
```

These are bandwidth-only lower bounds on time, hence upper bounds on throughput. Startup, fences, packet headers, reduction, memory traffic, imbalance and shared root/UPI capacity increase time. A measured rate in one probe is an engineering reference, not a proof of maximum physical capacity.

| Assumed balanced service rate | AR at 1 GiB | AG/RS at 1 GiB | Interpretation |
| --- | ---: | ---: | --- |
| Gen4 x16 encoded line rate ≈31.508 GB/s/direction | 51.12 ms | 25.56 ms | Optimistic GPU-only physical bound; no TLP overhead |
| Isolated copy rate 22.64 GB/s/GPU, if all sustain it | 71.14 ms | 35.57 ms | Aggressive scheduling target; concurrent achievability unproven |
| Measured ring aggregate 81.904 GB/s / 4 | 78.66 ms | 39.33 ms | Same-traffic engineering reference; not universal |

[NVIDIA specifies L4](https://www.nvidia.com/en-us/data-center/l4/) at 300 GB/s device memory bandwidth and PCIe Gen4 x16. The marketed approximately 64 GB/s PCIe number counts both directions; using it as one-direction payload capacity overstates the bound by roughly 2×. The table uses 16 GT/s × 16 lanes × 128/130 ÷ 8 before PCIe transaction overhead.

Relative to archived AR at 80.37 ms, the ring reference leaves only about **2%**; sustaining isolated-copy rates would allow about **13%** speedup. This does not justify claiming a 2× AR win from vectorization or reduction tuning. Fresh RS at 48.60 ms leaves about **24%** speedup to the ring reference and **37%** to the isolated-link target. Archived packet AG at 36.35 ms is already faster than the peer-ring reference, demonstrating why that reference cannot be called a hardware ceiling. Its physical endpoint bound is 25.56 ms, at most about **1.42×** speedup before overhead under this uncompressed workload.

For small messages, the bandwidth term is tiny: at 1 KiB the ring-reference terms are about 0.075 µs AR and 0.038 µs AG/RS. Observed 14–20 µs latencies therefore mostly reflect launch/submission/protocol costs. No measured graph or device-triggered floor is available here; a claimed 2–5 µs attainable latency would be speculation.

Host reduction changes the traffic model. Uploading four full inputs and broadcasting a host-reduced result uses N outbound and N inbound per GPU for AR, so the GPU-only 1.5N bound is not universal. The ideal endpoint bound becomes about 34.08 ms at 1 GiB, but CPU FP32 reduction, host memory, NUMA transfers and staging must sustain it. The measured DMA D2H service would alone take about 77.2 ms for four N uploads. Existing BF16 CPU reduction probes cannot establish FP32 performance. For packet AG, upload once/read three remotely entails N aggregate upload plus 3N aggregate download, with local shards retained on GPU. At 36.35 ms these are approximately 29.5 and 88.6 GB/s. This fits measured H2D capacity but does not prove a joint duplex limit; all traffic is SM mapped-memory traffic in that candidate.

There is also a socket cut bound. An ideal 2+2 hierarchy must move N useful reduced bytes per direction across the cut for AR, and N/2 per direction for AG or RS. If usable cut capacity is C, add t≥N/C or N/(2C). The current ring moves 1.5N per direction for AR, 0.75N for each half; flat AG/RS sends N per direction. Hierarchy reduces cut volume but can bunch traffic into a congested phase. An isolated cross-socket pair at 22.64 GB/s does not measure concurrent UPI capacity. A directional cross-socket saturation/duplex matrix is still needed before quoting a tighter topology ceiling.

**Implementation findings.**

| Code path | Concrete cost | Optimization to test |
| --- | --- | --- |
| `allreduce.cu: arHierPut` | Three globally phased exchanges, repeated grid barriers; cross-socket phase concentrates traffic | Independent tile/channel progress; overlap local reduction, cross-socket exchange and local gather |
| `arHierPort`, `arRingPort`, `publishToEngines` | Proxy FIFO handoff, waits, full-grid rendezvous; each ring step finishes receiving before next-step forwarding | Tile-wavefront forwarding, bounded credits and immutable send slots; fewer grid-wide synchronization points |
| AR launch configuration | Defaults 24×512 SM threads, 24×1024 LL threads; fixed 8 MiB ring pieces capped at 16 | Joint blocks/threads/piece sweep by size and competing compute load; tune startup and drain, not just steady state |
| `peer_ag_rs.cu: launchPeer` | One source stream per GPU, four serial destination copies, source completion only after all destinations | Chunked rotation with destination/tile readiness; controlled overlap with bounded number of peer destinations |
| `launchPeer` RS | 16 previous-reduction event waits plus up to 16 source-completion waits; then `sumFour` only after complete exchange | Ping-pong scratch with tile ownership, overlap receive and reduction; ring or recursive-halving RS |
| `sumFour` | Reads four full received shards in a separate scalar kernel; full-input-size scratch per GPU | Fuse receive/reduce/forward or reduce arriving tiles; vectorize only after fixing the pipeline |
| `pushSerialGather`, `pushSerialScatter` | One CTA controls ordering, but becomes the bandwidth bottleneck above medium sizes | Few-CTA coordinated phases or independent tile lanes; adding CTAs without scheduling can reintroduce fan-out collapse |
| `scatterFenceFused` | All three peer writes precede fence/flags and local reduction; one CTA; eager scratch reuse contract | Per-tile completion and reduction with bounded credits; preserve system-scope publication |
| Packet AG `consume` per-source branch | Source groups proceed independently, then a grid barrier joins all groups before reader credits | Per-source slot credits/queues, separate local copy, measured slot depth and block allocation |
| Configuration/selection | Hardcoded four-rank pairing and size exceptions, e.g. RS direct-self exclusions; benchmark-selected envelopes | Discover topology, cache calibration by exact identity, validate on held-out calls/sizes; explicit prepare and fallback |

Source references: [native AR](../src/collectives/allreduce.cu), [peer AG/RS](../src/collectives/peer_ag_rs.cu), [packet consumer](../src/cpu_router/packet_pipeline.cu). AR ring already overlaps reduction with subsequent incoming pieces *within a step*; proposing generic “pipelining” as wholly missing would be inaccurate. Packet AG already has per-source readiness, local-self retention, vector transfers and two-slot credits. CPU routing workers are absent in its GPU-progress Copy path; configured workers do not imply active CPU reduction.

The peer harness records start events on all devices before serial host enqueue, then end events after enqueue. Its reported CUDA-event time includes host gaps and source launch skew. `fill()` establishes device-ready inputs and each call completes before reuse. This does not prove arbitrary application-stream readiness or asynchronous back-to-back safety. The native AR harness measures host completion and checks rank-position-dependent inputs, but repeats the same input pattern; changed-generation randomized stress would be stronger for detecting stale scratch.

**Technique coverage and priorities.**

1. **First: pipeline large RS.** Compare current direct scatter + sum against three-step ring RS extracted from the tested AR schedule, and two-step recursive halving (N/2 then N/4). Both use 0.75N per GPU; topology and start/drain determine the winner. Try local pair reduction before cross-pair shard exchange to halve cut traffic versus flat scatter. Sweep 256 KiB–8 MiB pieces and a small range of channel counts. Target 39–42 ms at 1 GiB first, with 35–36 ms an aggressive hypothesis, not a promised result. GPU-memory traffic alone is too small to explain the entire 9 ms gap to the ring reference.
2. **Measure and remove small-message host work.** Pre-register/cache buffers and events, use caller streams, graph replay, one device protocol launch per GPU, and calibrated LL/direct modes. Compare paired eager and graph NCCL using the same input-ready boundary. Persistent progress is a further option for repeated workloads, but reserves SMs, needs cancellation/ownership and changes integration semantics. The packet module already supports graph-related machinery; the standalone FP32 measurements do not measure its best graph latency. [NCCL supports graph capture](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/cudagraph.html), with uniform capture participation across ranks.
3. **Optimize AG credits and routing.** Per-source reuse credits could remove all-source tail coupling; measure delayed-source cases before adding state. Test local peer + cross-socket host staging, one host copy per socket followed by local distribution, and recursive doubling or hierarchical gather. Host replication trades fewer remote reads against extra DRAM copies; require simultaneous duplex/NUMA measurements. Larger packets amortize protocol work but hurt overlap; more than two slots helps only if credit stalls dominate. Preserve the existing per-source negative results at 4/8 MiB.
4. **Reduce AR coordination costs.** Replace step-wide barriers with per-tile wavefronts only when traces show idle links. Tune proxy CPU affinity, NUMA placement, batching and queue contention. Test coordinated multiple rings/channel stripes and hierarchy/ring hybrids. More channels or both ring directions can oversubscribe root/UPI paths; the GPU endpoint stays shared. AR already has tree, hierarchy, LL, SM and CE variants; the missing work is better progress and validated selection, not merely adding their names.
5. **Prove publication before narrowing fences.** The source documents high system-fence cost and exposes fence modes. A passing run with `-F 1/2` is not a memory-ordering proof. Audit CUDA/MSCCL++ device release/acquire → proxy FIFO system release → copy-engine ordering, compiled instructions and sender lifetime. Retain immutable forwarding regions, iteration parity and registered subregions for 32-bit proxy offsets. Hopper memory synchronization domains are not an L4 solution: [NVIDIA documents hardware support beginning with Hopper](https://docs.nvidia.com/cuda/archive/13.1.1/cuda-programming-guide/04-special-topics/memory-sync-domains.html).
6. **Tune the actual memory path.** Coalesced 16-byte accesses, bounded polling, reduced register pressure, cache policy, alignment-aware bulk plus scalar tails, and balanced producer/consumer SM reservations. Avoid dropping the entire buffer to scalar accesses just because its tail is uneven. Experiment with CE+SM splitting only after measuring concurrent engine and root-complex contention. `cp.async` can help local staging/reduction, but cannot raise PCIe capacity or replace inter-GPU publication.
7. **Consider CPU reduction only with FP32 evidence.** NUMA-local partial reductions and cross-socket reduced shards can lower GPU traffic. Measure large-working-set FP32 reductions, simultaneous GPU upload/download, memory placement and worker saturation. The existing destination-interleaved BF16 GPU reduction experiment already improved flat staging but still lost to NCCL; it is not a missing technique or proof of a winning FP32 path. See [negative reduction-placement results](reduction-placement.md) and [GPU-progress comparison](baseline-comparison.md).
8. **Optimize application demand where permitted.** Bucket/coalesce small collectives; fuse producer→RS and AG→consumer; retain sharded tensors to eliminate an AG or replace AR with RS when consumers permit. Stream ready tiles to compute and measure compute slowdown from transport CTAs. Dense/MoE fusion prototypes already exist, but their timings are not standalone collective numbers. Compression, BF16 conversion or lossy quantization changes FP32 semantics; treat them as explicit workload options. Lossless compression cannot guarantee a gain for arbitrary input.
9. **Exclude unavailable hardware shortcuts.** No NVLink/NVSwitch appears in this topology. NVLS/multimem switch reduction, hardware multicast and SHARP do not supply a free local L4 reduction path. Query multicast support rather than assuming it from a CUDA version ([CUDA multicast API](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MULTICAST.html)). GPUDirect RDMA and network collective offload add a different route and hardware requirements; they are not established improvements for these local PCIe transfers.

**Experiments needed to tighten the bound.** Measure all three simultaneous peer permutations, intra-pair duplex, cross-pair duplex and mixed host/P2P traffic with explicit NUMA allocation, then sweep working-set and tile size. Capture a timeline for proxy enqueue, peer transfers, reduction, fence and credit waits; use targeted kernel counters only after identifying a kernel-bound phase. Compare current RS, pipelined RS, recursive-halving RS and an aligned no-reduction transfer control under identical timings. Report p50/p95 and run ranges with independently repeated windows; keep every losing variant. Separately test small eager, captured graph and device-triggered contracts. Never divide a graph candidate by an eager baseline.

Correctness acceptance for future changes must include all outputs, random rank/position/generation-dependent FP32 data, tolerance and reduction-order policy, 1008-byte and large uneven tails, in/out-of-place contracts, delayed ranks, back-to-back asynchronous calls, slot/sequence wrap, and graph replay where supported. Router edits additionally require policy/dispatcher checks and eager/graph tests. Calibrate by dtype, exact size, placement, topology and software identity; unknown cases must take a fallback without router initialization. These are future implementation gates, not claims that this analysis ran those tests.
