# GLM-4.5-Air-FP8 MoE epilogue plus RS (2026-11-12)

This is the first SGLang EP8 fusion path built on the packet NCCL proxy. The
SGLang hook keeps its FP8 MoE GEMMs and, when the layer's routed and shared
outputs are BF16, lets the GPU packet RS upload add them with BF16 rounding.
It avoids SGLang's separate `torch.add` output tensor. The local RS shard
stays on its GPU; the seven remote shards are uploaded as BF16 sums. Other
shapes and layouts use the original SGLang path. This is a MoE epilogue/RS
fusion, not the standalone dense GEMM+RS CUTLASS kernel.

## Validation and timing setup

- Hardware: one host with 8 NVIDIA L4 GPUs, 580.178.04 driver. The proxy was
  built with CUDA 12.9; SGLang's PyTorch 2.9.1+cu128 links NCCL 2.27.5. The
  proxy forwarded to that same NCCL binary. The model was GLM-4.5-Air-FP8
  with SGLang TP8/DP8/EP8, eager execution, packet AG/RS/AR, and
  `mem_fraction_static=0.93`.
- The server command requested at most 32 running requests. Its startup log
  reported an effective limit of 4 for this memory allocation in all three
  compared runs. This result is therefore not interchangeable with the
  earlier 32-running-request result in the main README.
- The eight-process `check-sum2` compares every BF16 output element with a
  materialized BF16 add followed by packet RS for 128 and 4096 elements per
  destination, including repeated calls on one stream. It passed after the
  vector upload and local-shard retention change. SGLang's warmup logged the
  new `RS_SUM2 count=4096` call on all eight ranks. A fixed temperature-zero
  16-token generation produced the same text with and without the hook.
- The [client](bench_e2e_workloads.py) submits deterministic prompts to
  `/generate`, records streaming timestamps, and includes client/server
  overhead in whole-batch time. Both workloads received three completed
  repeats per server. Server order was scalar-sum2, packet, optimized-sum2,
  packet. No request-level tracing was enabled during timed runs. The
  [24 raw results](fusion_rs_e2e_20261112.jsonl) include the initial scalar
  variant and every repeat.

## Whole-batch latency

| Requests:input:output | Initial scalar sum2 | Packet before | Vector sum2, retained local | Packet after |
| --- | ---: | ---: | ---: | ---: |
| 8:64:16 | 2.789 s | 2.704 s | **2.663 s** | 2.750 s |
| 32:512:64 | 14.770 s | 14.845 s | **14.474 s** | 14.879 s |

The values are three-repeat medians, not selected minima. The optimized
fusion is 1.5% and 3.2% below the packet controls for the short workload,
and 2.5% and 2.7% below the packet controls for the longer workload. The
initial scalar implementation regressed by 3.1% on the short workload and
was effectively tied on the longer one. These are small single-host gains;
additional workload shapes and independent days have not been measured.

## Small RS grid screening

A later eight-process BF16 screen compared the 4096-element-shard sum2 packet
kernel against a BF16 add kernel followed by packet RS. Each method used 20
warmups, 60 calls per timed round, and five interleaved rounds. CUDA events
recorded the full queued operation sequence; each value is the median of the
five slowest-rank per-call times, in microseconds. The add control is a simple
CUDA kernel with the same BF16 arithmetic, not PyTorch's exact launch path.

| Cooperative blocks | Add + packet RS | Sum2 packet RS |
| ---: | ---: | ---: |
| 8 | 46.080 | 46.029 |
| 16 | 45.022 | **44.134** |
| 24 | 46.131 | 45.346 |
| 32 (current default) | **44.544** | 44.612 |

The [40 raw samples](fusion_rs_block_sweep_20261112.tsv) retain the 118.716
and 89.924 microsecond control outliers. The 16-block option is only 0.478
microseconds faster than the 32-block sum2 median across separate runs; this
screen is insufficient to change the serving default. Set
`UCCL_LITE_RS_SUM2_BLOCKS=16` to test it explicitly at this shard size.

## Reproduce

Build and run the numerical check on eight idle L4s:

```bash
make -C integration/nccl_lite build/test_rs_sum2 \
  CUDA_HOME=/usr/local/cuda-12.9 \
  NCCL_HOME=$PWD/experimental/lite/build/nccl-2.28.9
make -C integration/nccl_lite check-sum2 \
  CUDA_HOME=/usr/local/cuda-12.9 \
  NCCL_HOME=$PWD/experimental/lite/build/nccl-2.28.9 \
  REAL_NCCL=/path/to/sglang-pytorch/nvidia/nccl/lib/libnccl.so.2
```

For the SGLang run, set `UCCL_LITE_REAL_NCCL` to SGLang's PyTorch NCCL
binary and launch through `run_sglang_rs_sum2_8l4.sh` followed by
`launch_glm45_air.sh --mem-fraction-static 0.93`. The hook is opt-in and
checks the source hashes of the two SGLang methods it replaces; an unknown
version leaves the original methods active.

The AllGather-plus-GEMM path is still separate. This report does not establish
an end-to-end gain from AG fusion or from the standalone BF16 dense kernel.
